## Goal

Saving an opportunity or a deal can never fail because of the other system's sync, and the sync failures are visible and repairable; an opportunity carries its product and a coded loss reason; every path that moves a stage leaves a history row; and the forecast has a daily record so a change in it can be explained later. Nothing existing changes shape; nothing is hidden; no new sidebar entry.

## Decisions (made by the assistant under the owner's "decide yourself" instruction; each reversible)

1. **The sync becomes bookkeeping**: a failure is caught, logged with the ids and the error, counted, and never reaches the person; a repair command re-runs it (dry run by default). Door: the wrapper can be removed.
2. **The required-fields rule is a config switch, OFF by default**: "an amount and a close date before a deal can enter Proposal" is written as a rule in config with the stages it applies to, default empty, so today's behaviour is unchanged until the owner turns it on.
3. **Forecast**: read the existing GTM forecasting tables (`2026_10_11_100000_gtm_forecasting`) first. Reuse them if they already keep what is needed (daily open, weighted and committed amounts per owner); add `g2g_forecast_snapshots` only for the part they do not keep, and say why in the slice log.

- DATA (dry run by default, `--apply`, per organisation, a re-run changes nothing, never overwrites a non-empty value): `opportunities:backfill-links` sets `product_master_id` from the opportunity's own product pointer if it has one, else from the converted lead's `product_master_id` (`crm_leads.converted_opportunity_id`), else from the signal's fit through the resolver; and maps an existing free-text `close_reason` to a code ONLY on an exact, documented match (the rest stays free text).

- NEW `g2g_forecast_snapshots` only if decision 3 finds it necessary.

## Contract (additive)

- `GET /api/crm/opportunities` and `/{id}` gain `product: {id, key, name}|null`, `loss_reason: {code, label}|null`; write validators accept `product_master_id` (visible to the organisation: its own or a shared product; 422 otherwise) and `loss_reason_code` (in the config list; required only when the config says so for Closed Lost, default not required).
- No existing key changes; a test pins the old keys.

## Acceptance

1. A failing sync never fails a save: with the bridge forced to throw, create, update and stage move answer exactly as before and the opportunity and its history are written; the failure is logged once per attempt; the repair command re-syncs and a re-run changes nothing. The same for the GTM `DealController` reverse sync.
2. Every path that changes `sales_stage` (kanban move, edit, conversion from a lead, GTM deal sync, bulk if any) writes one history row with from, to, amount, probability and close date; a test per path (an agent-read claim until then).
3. `product_master_id` and `loss_reason_code` validate against the organisation (cross-organisation product is 422) and are read back; the backfill's dry run, apply and re-run are shown on dev with counts.
4. The required-fields rule, when switched on in a test, refuses a move into Proposal without an amount or a close date with a field-keyed 422, and when off changes nothing.
5. Forecast: the decision, with the evidence of what the GTM tables keep; a daily snapshot command (dry run default) and a read endpoint only if new storage was needed.
6. Cross-organisation: another organisation's opportunity id is a 404 on every route touched.
