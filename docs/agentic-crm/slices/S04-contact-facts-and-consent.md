## Goal

Facts about contacts, organisations and leads (an email, a phone, a website, a LinkedIn address) are PROPOSED with evidence, shown to a person, and accepted or dismissed. A human-entered value always wins; a dismissed value is never offered again; every sender will pass ONE consent gate. The rules come from Comp AI (MIT): fixed weights per evidence kind, a noisy-OR score, bands verified / probable / possible.

## Contract (backend, what track S4b builds against; change it here first)

Same as `../briefs/S4a-facts-backend.md` section "Contract": `GET /api/facts/entity/{type}/{id}`, `GET /api/facts/queue`, `POST /api/facts/{id}/accept`, `POST /api/facts/{id}/dismiss`, `GET /api/consent/{type}/{id}`; the Fact shape; rights through the existing Contacts and Organizations rows; another tenant's id answers 404.

**Additions made by S4a (4 Nov 2026, all additive; the brief's shapes are unchanged, S4b may ignore what it does not need):**
- **Routes.** `GET /api/facts/entity/{type}/{id}` and `GET /api/consent/{type}/{id}` are registered as three literal routes each (`.../contact/{id}`, `.../organization/{id}`, `.../lead/{id}`), so the route middleware carries the right of the screen the type belongs to (a `{type}` placeholder cannot be mapped to a different menu row by `platformright`). The URL a client builds is exactly the one in the brief; any other type is a 404. Rights: contact = `/module/crm/marketing/contacts` OR `/module/crm/support/contacts`; organization = `/module/crm/marketing/organizations` OR `/module/crm/support/organizations`; lead = `/module/crm/marketing/leads`. View reads, edit decides.
- **Queue and decisions** have no single entity type, so their route middleware is the OR of the three edit (or view) rights and the controller then checks the right of the fact's own type: the queue lists only the types the caller may view (`type=` of one they may not view is 403); accept and dismiss answer 403 `{code:'no_right'}` when the caller may edit some type but not this fact's, and 404 for another tenant's id, as ever.
- **Fact** also carries: `field_label` (string), `rationale` (string, plain English from the weights), `column_written` (bool: this fact wrote the target column when accepted; false means it is kept in the ledger only), `record_value` (string|null: what the target column holds now, so a person sees the record next to the suggestion; null when the field has no column on that record type), `decision_note` (string|null: the dismiss reason), `supersedes_id` (int|null), `created_at`. A queue row also carries `entity_name`.
- **Decision answers.** `POST .../accept` and `.../dismiss` answer 200 `{status:1, data:{outcome:'applied'|'dismissed', fact}}`; a fact that is not waiting answers 409 `{status:0, code:'not_pending', message, data:{fact}}`; accepting a fact whose record has been removed answers 409 `{code:'entity_gone'}` and changes nothing.
- **`can`** (added 4 Nov at track S4b's request): `GET /api/facts/entity/...` answers `data.can = {decide: bool}` (edit right on that kind of record); `GET /api/facts/queue` answers `data.can = {decide: bool, decide_types: list<string>}` (the kinds the caller may BOTH view and edit). The server still enforces every decision.
- **Consent channel** also carries `code` (string|null: `opted_out`, `suppressed`, `suppression_list`, `outreach_contact_blocked`, `preference_opted_out`, `no_consent_recorded`, `no_address`, `unknown_recipient`).
- **Proposing** (`FactWriter::propose`, called by the agent tool of S7 and the discovery sources of S5; there is no HTTP route that proposes) returns an `outcome` string, one of: `stored`, `refused_dismissed`, `refused_waiting`, `refused_on_record`, `refused_replaced`, `refused_below_floor`, `refused_value`, `refused_field`, `refused_evidence`, `refused_entity`.

**Decisions made while building (each reversible, all in code and config):**
- **D7 Accept writes the record column only when it is blank, and records whether it did (`column_written`).** A person who accepts a fact for a column that already holds a value leaves the record alone: the fact is kept as applied in the ledger (it is true and evidenced) and the screen shows `column_written = false` next to `record_value`. For a ONE-value field (`one` in `config/facts.php`: title, linkedin_url, employer, location) the newly accepted fact SUPERSEDES the previous applied one in the ledger, which can leave the ledger ahead of the record (the record keeps what a person typed). The alternative (replace a value the ledger itself wrote and nobody changed) was NOT taken, because the brief and D2 say "only when blank"; it is a one-line change in `FactWriter` if the owner wants job changes to flow into the record. Many-value fields (email, phone, website) never supersede: two addresses can both be true.
- **D8 Proposals are not refused because the record already has a different value** (the original refuses: "a person already filled in X"). G2G has no auto-apply (D3), so every proposal waits for a person, who sees the record's value beside it (`record_value`); an alternative address for a school is information. A proposal equal to what the record holds is refused (`refused_on_record`), and so is one already waiting, applied, dismissed or replaced (the unique key, read first).
- **D9 Consent defaults.** Email is allowed unless an opt-out, a suppression or a blocked outreach contact exists (today's behaviour, so nothing that works stops working); SMS and WhatsApp are NOT allowed until an `opted_in` preference is recorded for that channel (they are opt-in channels), and an opt-out beats an opt-in. A record without an address or number is not allowed (`no_address`). Whether email should also become opt-in is a legal question for the owner at S10.
- **D10 Score is rounded to 3 decimals before the band is read; the same kind of evidence from the same address counts once** (deviations from the original, tested).
- **D11 Two evidence kinds added for G2G** (`site.own-page` 0.80 primary, `directory.listing` 0.55): an organisation's own website is the authority on its own contact details; the weights are judgement and S5 calibrates them against a real answer key.
- **D12 `linkedin.employer-and-name` is kept as a kind** (it is how a licensed enrichment source or a person who read the profile reports it) though nothing in G2G fetches LinkedIn; the static test proves it.
