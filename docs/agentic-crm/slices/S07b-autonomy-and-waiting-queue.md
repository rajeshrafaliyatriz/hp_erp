## Decision (made by the assistant under the owner's "decide yourself" instruction; reversible, UI only)

The owner's rule is "no duplicate screens". The plan's two new screens (Settings > Agents, Today > Proposals) are therefore folded into the EXISTING **Agent Run History** screen (`/module/crm/marketing/agent-runs`) as tabs: **Runs** (as it is), **Waiting for you** (every proposal nobody has decided, across organisations, with accept / dismiss), **Autonomy** (administrators only). No new menu row. Door: if the owner wants a separate Settings entry, it is a move of one component, not a rebuild.

## Why (the user's labour)

Today a proposal can only be decided from inside one organisation's page, and the level of an action can only be changed by writing a database row (`agent_autonomy_check.php`). A person who wants to clear the day's proposals has to open organisations one by one; an administrator who wants to let the agent act alone more (or less) has no screen and no evidence for the choice.

## Starting facts (4 Nov, read in source)

- Routes: `routes/agent_gateway.php` (prefix `api/agent`): organisation state, run, `POST /proposals/{id}/accept|dismiss` (EDIT on Organizations), `GET /runs`, `GET /runs/{id}` (VIEW on the run-history row). `AgentGatewayTenantSweepTest` walks this file's routes and fails for an id route without a tenant filter or rights middleware.
- Levels and defaults: `config/agent_actions.php` (`actions`: add_note alone, add_task alone, confirm_link approval; `levels`: off, suggest, draft, approval, alone). Overrides: table `g2g_agent_autonomy` (`action_key`, `level`, tenant; `action_key = '*'` and level `off` is the organisation's kill switch; organisation 0 switches the agent off for everybody). `AutonomyPolicy` reads it.
- The decision code: `ProposalDecisions`, `ProposalApplier` (exactly-once claim), `AgentAudit`, `AgentEvents`.

## Contract (S7b-api builds it; S7c reads it; additive, nothing existing changes shape)

All routes `api` + `api.token`. Rights: reading = VIEW on the run-history row; changing a level or the kill switch = EDIT on the run-history row AND an administrator of the tenant (read how `AgentAccess` and the platform services decide "administrator"; never read `role_key` raw, see `SubjectAuthority`); deciding a proposal = EDIT on Organizations, as the existing accept / dismiss.

- `GET /api/agent/autonomy` -> `{status:1, data:{kill_switch:{on:bool, scope:'organisation'|'platform'|null}, actions:[{key, label, description, default, level, overridden:bool, levels:[...], counts:{proposed, applied, accepted, dismissed, failed}, last_changed:{at, by_name}|null}], can:{change:bool}}}`. `counts` are the last 30 days, from `g2g_agent_tool_calls` and `g2g_agent_proposals` (the evidence for raising or lowering a level). Labels and descriptions are plain English from the config.
- `PUT /api/agent/autonomy/{actionKey}` body `{level, reason?: string<=300}`: upserts the override (setting a level equal to the default removes the override), audited (`AgentAudit`) and recorded as an event `agent.autonomy.changed` (register it in `EventCatalogue::SHIPPED` the way the other agent events are), answers with the same action object. 404 for a key that is not in the config; 422 for a level not in `levels`; 403 for a non-administrator. There is NO way to create an action: a key outside `actions` is refused.
- `PUT /api/agent/autonomy-kill-switch` body `{on: bool, reason?}`: writes or removes the `*` row for the tenant (never the platform row 0: that one is not changeable from a screen), audited and recorded the same way.
- `GET /api/agent/proposals?status=pending&page=&per_page<=50`: the tenant's proposals, newest first, each `{id, run_id, action, label, summary (plain words, built from the payload by the presenter that already exists), organisation:{id, name, href_hint}, evidence:[...as the organisation panel shows], created_at, can:{decide:bool}}`; `data:{rows, pagination}`. A proposal whose organisation was removed is shown as such, not dropped silently.

## Acceptance

1. A level changed through the API is what `AutonomyPolicy` then applies (an end-to-end test: set `add_note` to `approval`, run the agent service with the fake model, see a pending proposal instead of an applied note; set it back, see the default).
2. Every change writes an audit row and an event; the wrong tenant's key, a non-administrator, an unknown key and an unknown level are refused with the right status; the kill switch stops a run and a decision on a new run.
3. The queue lists only the caller's tenant; deciding a proposal from the queue uses the existing accept / dismiss (no second apply path) and is exactly-once under a race.
4. `AgentGatewayTenantSweepTest` still passes and covers the new id route(s).
5. Front end (S7c): the three tabs on Agent Run History, the queue clears without opening organisations, the Autonomy tab shows counters beside each level and a plain-English warning on "alone"; administrator-only; light and dark; 390 px.

- 2026-11-04 (tasks 2 to 5, built and saved in increments; every file below was written, then its tests run). **Design decisions found while building (each with its reason):**
  1. **`AutonomySettings`** (`app/Domain/AgentGateway/AutonomySettings.php`) holds the state and both writers; the controller stays thin. It reads and writes the same `g2g_agent_autonomy` rows `AutonomyPolicy` reads, so there is no second policy: a level changed here is what the next run and the next Accept apply (proved end to end in `AgentAutonomyApiTest::test_a_level_changed_through_the_api_is_what_the_agent_then_applies`: default alone -> note written; approval -> proposal waits, no note; off -> `policy_off`, nothing stored; back to default -> row removed, note written).
  2. **"Default" is what applies with no row of the organisation's own: the shared row (organisation 0) if there is one, else the config.** Without this, "a level equal to the default removes the override" would be wrong when a shared row exists (choose `alone` where the config says `alone` but the shared row says `approval`: removing the row would leave `approval`). `AutonomyPolicy::setting()` returns `{level, default, overridden}`.
  3. **The screen shows the CONFIGURED level even while the kill switch is on.** `AutonomyPolicy::level()` answers `off` for everything when the agent is switched off, so the state reads `setting()` instead; `level()` now calls `setting()`, so there is one rule.
  4. **`kill_switch.scope` is `platform` when the shared row is off, even if the organisation's own is too** (the organisation's switch cannot bring the agent back while the platform's is on, and the screen must say who holds it). `AutonomyPolicy::killScope()`; `killed()` is derived from it.
  5. **Audit and event of a settings change.** `AgentAudit::forSettings($tenant)` writes a `g2g_agent_tool_calls` row with `run_id = 0` (no run has id 0, so a run's trail never shows it), tool `set_autonomy` / `set_kill_switch`, args `{action, from, to, reason?, by}` (the table has no actor column, so `by` is in the args), `result_ref = g2g_agent_autonomy:{row id}`. `AgentAudit::record()` now returns the id of the row it wrote (was void; no caller used a result). The event `agent.autonomy.changed` (registered in `EventCatalogue::SHIPPED`, PROJECTOR) carries `{action, from, to, reason?}` and the actor; **its idempotency key is `agent.autonomy.changed:{tenant}:{audit row id}`**, not the setting's id: a setting is changed many times and a key naming it would silently lose every change after the first (the g2g_event trap in memory). Both are written in the SAME transaction as the change. A request that changes nothing writes nothing.
  6. **The kill switch's `from` / `to` are `running` / `stopped`** (plain words in the audit log), and its action is `*`.
  7. **`last_changed`** is the newer of (the newest `agent.autonomy.changed` event of the organisation for that action, which also covers a level put back to its default when no row is left) and (the override row's own `updated_at` / `updated_by`, which is how a hand-made change shows). `by_name` is looked up tenant-scoped, so a person of another organisation is never named. **No migration was needed:** `g2g_agent_autonomy` already has `updated_by` and `updated_at` (verified on dev).
  8. **`counts`** are the last 30 days of `g2g_agent_proposals` of the organisation (one row per action the agent asked for): `proposed` = all of them, `applied` = carried out (by the agent alone OR accepted), `accepted` = the part of `applied` a person accepted (`applied_via = user`), `dismissed`, `failed`; a pending one is only in `proposed`. I did not read `g2g_agent_tool_calls` for counts: every kept ask is a proposal row with its fate, and a denied call (for example `policy_off`) is not an ask the gateway admitted. A row for something that is not an action is ignored.
  9. **The administrator check is in the controller** (`AgentAccess::isAdministrator`, through `RoleKey::forProfileId` as `ProductAccess` does, never a raw `role_key`), before the key and the level are looked at. `can.change` = EDIT on the history row AND administrator (`AgentAccess::canChangeAutonomy`). On dev tenant 6 the HR profile (18) holds EDIT on the history row, so the right alone would have let HR set levels.
  10. **Response shapes where the contract was silent:** `PUT /autonomy/{actionKey}` answers `data` = the action object itself (the same object `actions[]` holds); `PUT /autonomy-kill-switch` answers `data = {kill_switch: {on, scope}}`. Refusals: `{status: 0, code, message}` with `administrators_only` 403, `unknown_action` 404, `unknown_level` 422, `no_organisation` 403 (an organisation of 0 is the shared row: never changeable from a screen); validation of the body's shape (level required string, `on` required boolean, reason a string of at most 300 characters) is 422 with `message` and `errors`.
  11. **The queue** (`GET /api/agent/proposals`): `data = {rows, pagination: {page, per_page, total, last_page}}`; `status` is one of `pending` (default), `applied`, `dismissed`, `failed`; `per_page` capped at 50.
