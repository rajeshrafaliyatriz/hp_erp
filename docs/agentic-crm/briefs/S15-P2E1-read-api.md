## Goal
The screens of P3 (list, Sub-product page with six tabs, the shared product picker, redirects) call ONLY these endpoints. Today the reads are unpaged and nested, gated entirely by the Products row's right (HR gets 403 on the Portfolio), `GET /{id}/usage` lacks orders and invoices, there is no unified history and no way to find a record from an old CRM id. Build them with these exact contracts (JSON `{status, data, meta?}` like the neighbours):
1. **`GET /api/product-master/list`** (paged, flat): query `page`, `per` (5 to 100, default 20), `q` (name, SKU, offer id), `productId`, `type` (`subproduct`|`service`|all), `sold` (`yes`|`no`|`paused`), `readiness`, `status` (`active`|`archived`). Row: `{id, kind, name, key, productId, productName, type (product|service|null), state (not_sold|sold|paused|binned), readiness, signalsFound, icp (state), hasAbout, hasSell, needsProduct (no Product yet)}` plus, ONLY for a caller who may view the Sell section of that row's type (`ProductAccess::canViewCatalogue`): `sku`, `unitPrice`, `currency`. A level-1 Product is a row with `kind=product` and its sub-product count. `meta` has `total`, `page`, `perPage`, `lastPage` and `can` (`createProduct`, `createSubProduct`, `viewSell`, `confirmMatches`). Tenant-scoped (its own and shared Products); a request for `per` over 100 is clamped.
2. **`GET /{id}`** (show): the record with `about`, `icp` state and `sell` ONLY for a caller who may view Sell (key always present, null otherwise); it must not return the ungated `crmProduct` (P2-C open item, ProductMasterController show about line 189): keep the key for the OLD drawer only when the caller may view Sell.
3. **`GET /{id}/sell`**: the Sell section for a caller who may view it (403 otherwise), via `CatalogueFields::toSell`.
4. **`GET /{id}/history`** (G-2): one list, newest first, of the audit lines of the three stores of this record (entity types the writer files: `crm.product*`, `portfolio.offer*`, `product.master*`; read `ProductWriteAudit` and `HasCrmAuditTrail::history`), each `{at, by, store (about|sell|record), event, changes:[{field, old, new}]}`; lines of the `sell` store (and any `unit_price`, `cost_price`, `commission_rate` change) only for a caller who may view Sell. Paged (`page`, `per`).
5. **`GET /{id}/usage`** (G-3): extend the existing answer with orders, invoices, purchase orders, opportunities, tickets, assets, FAQs and bundle rows next to the signals, ICP, price books and quotes it has; counts for every table of `ProductPointers::toCrmProduct()` plus the latest 5 documents of each of quotes, orders and invoices (number, date, status, link id); only for a caller who may view Sell (403 otherwise); an About-only record answers its signals and ICP only.
6. **`GET /by-crm/{crmId}`**: `{id (master id), kind}` of the master row that holds this catalogue id (also a binned item), tenant-scoped, 404 otherwise: it serves the permanent redirects of the old product addresses.
7. **`GET /picker?type=&q=&limit=`**: sold, active, not binned catalogue-backed Sub-products for the document pickers: `{crmProductId, masterId, name, productName, sku, unitPrice, currency, taxRateId, type}`; `limit` default 20, max 50; search-as-you-type on name and SKU; requires `canViewCatalogue` of the type asked (the same right the old `/crm/products?itemType=` picker needed); a `crmProductId` that an old document already holds but that is paused or binned is still resolvable through `GET /{id}`/`by-crm`, not offered here.
8. **Re-gate the existing reads** (`/`, `/lines`, `/options`, `/meta`) to the signed-in token plus the tenant scope: names, ids and lines are open to any signed-in user (HR must be able to open the Portfolio); everything priced or Sell-related stays behind `canViewCatalogue`. `meta()` `can.createSubProduct` must follow the writer's real rule (a person who may add About or Sell), not "screen add AND portfolio right" (P2-C open item, about line 174).
