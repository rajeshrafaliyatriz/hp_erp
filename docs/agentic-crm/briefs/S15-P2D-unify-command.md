## Goal

## 2. Suggestions (pure code, no writes)
`app/Domain/ProductMaster/ProductMatchSuggester.php`: for one organisation, for each LIVE catalogue item (a master row of kind `item` whose CRM row is not in the Bin), candidates are the Sub-products (kind `sub_product`) of the SAME Product that hold no CRM pointer yet. Signals, each with its own weight and a short reason string: the item's category inside the candidate's name; content words shared after removing the Product's brand words (for ScholarClone: "scholar", "scholarclone"; take the brand words from the parent Product's name/key, do not hard-code them) between the item's name and description and the candidate's name, `what_it_does` and `modules_components`; the item's SKU against the candidate's `offer_id` tokens; the item's price against `typical_deal_band` (a hint, small weight); a SERVICE never matches a non-service (the candidate is a service only if its offer says so: read how services appear in the data, and say what you found). Usage counts (opportunities, quotes, orders, invoices, tickets, assets, FAQs, price books, bundles) protect an item but never create a match. Assign one-to-one by best score with a margin over the runner-up; below the margin the verdict is AMBIGUOUS; two items that share a best candidate are EDITION. Verdicts: `MATCH-HIGH`, `AMBIGUOUS`, `EDITION`, `SERVICE`, `NO-MATCH`, `STRAY` (no Product), `JUNK?` (report only: a name like "ZZ ..." or test words). Name-only matching is unsafe (the shared brand word inflates every pair, editions share a category, acronyms such as "LMS-PAL" versus "LMS & Digital Classroom" are missed): the tests must show each of those four cases.

## 3. The merge (one pair, one transaction)
`app/Domain/ProductMaster/ProductMerger.php`: `merge(identity, itemMasterId, survivorMasterId, nameKept)`. Under row locks, in this order: validate both rows are the organisation's own, the survivor is a `sub_product` with an offer row and NO CRM pointer, the item is a live `item` with a live CRM row, and the Products agree or the item has none; take a pointer census (`ProductPointers`); free the unique `crm_product_id` slot (the item's master row becomes a husk: `status archived`, `origin merged`, `crm_product_id` NULL, `offer_row_id` NULL); set the survivor's `crm_product_id`; mirror the kept name (portfolio by default) and the Product to the offer row and the CRM row with the mirror method P2-B2 added; repoint every `product_master_id` pointer that holds the husk's id to the survivor's id (the list is `ProductPointers::toMaster()`, EXCEPT `crm_products.product_master_id`, which means the Product and is never repointed); where `g2g_product_claims` would collide on `(tenant, product_master_id, claim hash)` keep the survivor's and retire the duplicate row; write the `different`/`same` decision row; run `ProductIntegrity::check()` for the organisation INSIDE the transaction and roll back if it reports an error; commit; after the commit emit the audit event through `EventRecorder`. **Never deleted:** the CRM row (11 tables point at it), the offer row, the husk, any claim. Re-running a merge already done is a no-op. `different` writes only the decision row and the pair is not offered again. `--rollback` (below) undoes a merge.

## 4. The command and the review API
Command `product-master:unify {--tenant=} {--database=} {--map=} {--apply} {--rollback=}` in `app/Console/Commands/ProductMasterUnifyCommand.php`: **dry run by default**; prints and saves a report with the columns: Product, CRM id, product no, name, SKU, type, price, live or binned, the usage counts, candidate Sub-product, per-signal scores, margin, verdict, plus a second table of Sub-products with no CRM match. `--apply` merges only the pairs named in `--map=<file>` (a small JSON/CSV the owner confirms: item master id, survivor master id, name to keep), never a suggestion on its own. Before `--apply` writes anything it saves a JSON snapshot of every row it will touch (a folder under `storage/app/product-master-unify/` with a timestamp, outside git), and `--rollback=<snapshot>` restores exactly those rows and removes the decision rows it made, then runs the checker. Refuse any host other than the dev host unless `--database` is named (copy the guard of `product-master:check`, `ProductMasterCheckCommand::refusal`). Review API for the P3 screen: `GET /api/product-master/matches` (suggestions with reasons, plus decisions already taken) and `POST /api/product-master/matches/decide` (`itemMasterId`, `survivorMasterId`, `decision`, `nameKept`), both administrators only (`ProductAccess::isAdministrator`), in a new controller `ProductMatchController` and a new route block appended to `routes/product_master.php` (do not re-order or edit the existing blocks).
