## Design (decided; justify any deviation in the report)
- **Pipeline, no free-form tool loop in v1:** (1) `OrgAgentContextBuilder` assembles a bounded, tenant-scoped, read-only context from the Organisation 360: sources and link bases, signals (title, status, event date, verbatim quote, source URL), open deals, last notes, open tasks, contacts count, last activity date; every fact carries a ref `{type, id, url}`. (2) ONE model call through `AiModelClient` returns schema-validated JSON: a brief (about 600 characters) and up to 5 proposals; token cap per run; cost recorded in rupees through the existing pricing chain. (3) `Gateway` validates every proposal: action in the whitelist (`add_note`, `add_task`, `confirm_link`); the target is the subject organisation only; text length-capped, stored as plain text and rendered as text; every cited evidence ref must exist in the context that was sent (a proposal citing anything else is dropped: anti-hallucination); task due dates valid and within a sane window. (4) Policy from `g2g_agent_autonomy`, defaults in `config/agent_actions.php`: `add_note` = alone, `add_task` = alone (the owner's standing default: agents act alone only for notes and tasks, admin-editable), `confirm_link` = approval; a row `action_key='*'` at level `off` is the per-organisation kill switch. "Alone" applies through `RecordNote` and `RecordTask` at once with `created_via='agent'`; "approval" waits as a pending proposal. (5) Accept applies through the same services as the acting user (needs the edit right on Organizations); Dismiss stores an optional reason, and the same proposal (same subject, action and payload hash) is never offered again (unique key).
- **Safety:** signal text and anything web-derived is UNTRUSTED data: put it in a delimited data block, tell the model to treat it as data, and never let model output choose an action outside the whitelist, a tenant, or a target outside the subject. The tool registry contains NO tool whose name includes send, email, sms, delete or merge, and a test lists the registry. If the model is unavailable or unpriced the run is `unavailable` with a clear message and no proposals. A per-organisation daily run cap is in config.
- **Tables (dev only, already applied, batches 560 to 564):** `g2g_agent_runs`, `g2g_agent_proposals`, `g2g_agent_tool_calls`, `g2g_agent_autonomy`, plus `crm_organization_comments.created_via`. Migrations `2026_12_10_090000` to `2026_12_10_090400`. Change them only with a NEW migration file (they have run on dev); `down()` stays tested.
- **API** (`routes/agent_gateway.php`, `api` + `api.token`): `POST /api/agent/organisations/{orgAccountId}/run`, `GET /api/agent/organisations/{orgAccountId}`, `POST /api/agent/proposals/{id}/accept`, `POST /api/agent/proposals/{id}/dismiss`, `GET /api/agent/runs` (+ filters and paging) and `GET /api/agent/runs/{id}`. Rights: run, accept and dismiss need edit on the Organizations rows; reads need view on them; the runs list and detail need view on `/module/crm/marketing/agent-runs`. Every by-id read filters by tenant and answers 404 for another tenant's id; a route-sweep test covers this file.
