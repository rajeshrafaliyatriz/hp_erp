## D6. Merging two products repoints 2 of the 12 pointers
`CrmProductController::merge()` (about :474-522) passes a `repoint` closure to `mergeRows` that updates only `crm_opportunity_products` and `crm_quote_line_items`. The other 10 columns that point at `crm_products.id` keep pointing at the merged-away product, which is now in the Recycle Bin: `crm_sales_order_line_items`, `crm_purchase_order_line_items`, `crm_invoice_line_items`, `crm_price_book_items`, `crm_product_bundle_items` (both columns), `crm_tickets`, `crm_assets`, `crm_faqs`, `crm_campaigns.product_id`. The registry is `app/Domain/ProductMaster/ProductPointers.php::toCrmProduct()` (P2-A; each entry says how the organisation is found, own column or a parent document): drive the repoint from it, so a new pointer cannot be forgotten.
Wanted:
- Every registered pointer at the duplicate moves to the survivor, scoped to the organisation (never touch another organisation's rows).
- Unique keys must not break the merge: `crm_price_book_items (price_book_id, product_id)`: when the survivor is already in that price book keep the survivor's row and drop the duplicate's; `crm_product_bundle_items (parent_product_id, component_product_id)`: same rule, and a repoint that would make a bundle contain itself deletes that row. Read the migrations of every table for other unique keys (for example `crm_opportunity_products`) and handle each the same way; say in the log what you found.
- A SCAN test: every column of `ProductPointers::toCrmProduct()` is either repointed by the merge or listed with a written reason; adding a pointer to the registry without handling it fails the test.
- After a merge, `(new ProductIntegrity(...))->check()` is clean for that organisation (put that assertion in the test), line-item COUNTS per table are unchanged, and the survivor's total of referencing rows equals survivor plus duplicates before.
- The master side: the duplicates' own master rows follow the existing `ProductMasterSync::throughCatalogueItems` call that `merge()` already makes; do not change that behaviour except where a test proves it wrong.

## D7. A rename is mirrored in one transaction
`ProductMasterSync::catalogueItem()` (about :198-209) was widened on 5 Nov (`0826227a`) so that a CRM-item rename also renames the master row of a SUB-PRODUCT that holds that item, but not the Portfolio offer: master and offer then differ (the checker's I5). The other direction (`offer()` about :219-301) renames the master row and pushes the parent to the item, but not the name. The owner's rule (13 Nov): ONE record. A name has one value; whichever door changes it, the master row, the offer row and the CRM item of a row that holds them all change together, in ONE database transaction, so no reader ever sees them differ. A row that holds only one pointer changes only what exists. A catalogue-only item never renames a different record.
Wanted: a single small method in the ProductMaster domain that applies a rename (and a parent change) to every copy that exists, used by `catalogueItem()` (CRM door) and `offer()` (Portfolio door) and by nothing else yet (P2.4's writer will call it). Errors inside it must not be swallowed on THIS path (the legacy "guarded" wrapper that logs and continues stays for the other, optional steps: read `ProductMasterSync::guarded`), but the legacy endpoints must still answer as before when the sync is unavailable (a host without the master table).
**Rewrite the stale test** `tests/Feature/ProductMasterSyncTest.php::test_editing_renames_the_catalogue_item_but_never_the_name_of_a_sub_product_that_uses_it` (it pins the S1 rule "linked, not merged", superseded by this decision): new name `test_a_rename_from_either_door_is_mirrored_to_the_master_row_the_offer_and_the_item_and_never_to_a_different_record`, with the checker clean afterwards, a rename from the Portfolio door mirrored to the item, a catalogue-only item renamed alone, and a rename that fails half way leaving all three unchanged (use a forced failure) because it is one transaction. Keep the old test's history in a comment (date, decision, why).
