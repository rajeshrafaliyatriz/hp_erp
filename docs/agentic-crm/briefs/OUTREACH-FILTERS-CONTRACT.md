## The four filters: ONE definition (Track F, a pure-ish class `app/Domain/Signals/Outreach/OutreachFacets.php`, used by all three screens so a chip, a count and a row can never disagree)
A row (company, person or message) has a SET of values per facet. A filter passes a row when the set contains the value; the value `none` passes a row whose set is EMPTY ("Not recorded"). Filters are ANDed. An unknown value matches nothing (no error).

| facet | query param | value | set of a COMPANY (from its non-deleted signals + the company row) | label |
|---|---|---|---|---|
| Product | `product` | master id (kind product) or `none` | each signal's `product_master_id` (a sub_product master id resolves to its parent product); else its `product_key` matched to a product master (`product_key` or `signal_key`, tenant or tenant 0); else nothing | the product's name |
| Sub-product | `sub_product` | sub-product master id, or `offer:<code>` for a code with no master, or `none` | each signal's `COALESCE(offer_id, relevant_offer_id)` resolved to a sub-product master through `g2g_product_offers.offer_id` + `g2g_product_master.offer_row_id`; a signal whose `product_master_id` is itself a sub_product master also counts; an unresolvable code is `offer:<code>` labelled with the offer's `name` or the code | the sub-product's name |
| ICP | `icp` | `b2b`, `b2c`, `b2g` or `none` | each signal's lower-cased `customer_model` when it is one of the three | `B2B: Private organisations`, `B2C: Consumers`, `B2G: Government and tenders` |
| Region | `region` | a region key (lower-cased, trimmed, spaces collapsed) or `none` | the `country`, `state` and `city` of every entry of each signal's `region_scope` JSON, plus the company's `state`, plus each comma-separated part of the company's `location` (`Nagpur, Maharashtra` gives `Nagpur` and `Maharashtra`); skip empty, numeric-only or over-60-character tokens | the first spelling seen |

- A **person** (signal contact): the sets of its company, plus its own signal's (`opportunity_id`) and its own `location` as a region token. A manually added person with no company: empty sets.
- A **message**: its own `product_master_id` is authoritative for Product (a sub_product master id gives that sub-product AND its parent product); the other facets (and Product when the message has none) come from the person whose `gtm_contact_id` equals the message's `contact_id`, through that person's sets; a message whose contact is not a signal contact has empty sets for those facets.
- **Cascade rule (the front end applies it, the backend accepts any combination):** the Sub-product options shown are the ones of the selected product (when a real product is selected); choosing another product clears a sub-product that no longer belongs.
- **Facet options with counts (`facets`)**, returned inside the same list answer: `{ products: [{value,label,count}], subProducts: [{value,label,count,productId}], icps: [{value,label,count}], regions: [{value,label,count}], notRecorded: {products,subProducts,icps,regions}, active: {product,subProduct,icp,region} }`. Each facet's counts are computed with the OTHER three facets applied and not itself (so picking an option never promises rows it does not have), over that screen's rows BEFORE the chip, search and paging. Options with a count of 0 are left out, except the currently selected one. Regions: the 50 most common (by count, then name) plus the selected one. Sorted: Product and Sub-product by name, ICP B2B/B2C/B2G, Region by count then name.
- Order in the pipeline of each list: base rows -> **facet filters** -> summary counts (the chips' counts follow the facet filters, so a chip count equals what you would see) -> chip -> search -> sort -> page.
