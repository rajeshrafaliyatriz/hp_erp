# Visual regression of the two global `components/ui` edits (track X, 3 Nov 2026)

Why: the owner's rule says the Signals screen design is frozen. Two edits asked for by the S3 browser defects live in shared code that the Signals pages also render through the shell: D5 `components/ui/breadcrumb.tsx` (wrap the items in an `<ol>`) and D1 `components/ui/confirm-dialog.tsx` + `alert-dialog.tsx` (Cancel through `AlertDialogCancel`). The caller's condition: they must look identical on `/signals`, `/ingestion`, `/portfolio`, `/partners`, with a before and an after capture, or D5 does not ship.

Method (tag: verified, I ran it): a real Chromium (Playwright) as the tenant-6 administrator against the local dev stack. Script `D:\dev\agentic-crm-research\scripts\browser\x-ui-visual.cjs` (`capture ... before` with `components/ui` untouched, then the edits, then `capture ... after`, then `compare`). For every breadcrumb node: its box (position and size relative to the nav) and 42 computed style properties; plus a pixel-by-pixel comparison of the element screenshots. Throw-away harness route `app/zz-x-ui-harness/page.tsx` (deleted at the end of the track) renders the real shared `ConfirmDialog` and the real shell `GtgBreadcrumb` with short and long labels at fixed widths 160, 240, 320, 480 and 800 px, the hardest layout cases.

Raw files and the full compare output: `D:\dev\agentic-crm-research\evidence-s3\browser-folded\` (`ui-before.json`, `ui-after.json`, `ui-visual-compare.txt`, `bc-*`, `hbc-*`, `dlg-*`, `page-*` PNGs).

## Findings

1. **Which Signals pages reach which component.** All four frozen pages (`/signals`, `/ingestion`, `/portfolio`, `/partners`) render the shell breadcrumb (`Home > Sales & Marketing Intelligence > Market Signals`): affected by D5. None of them reaches the shared `ConfirmDialog` or the Radix `AlertDialog`: the Ingestion Engine, Product Portfolio and its ICP editor use the browser's own `window.confirm` (read in source: `ingestion-engine-view.tsx:205`, `portfolio-view.tsx:159,173`, `product-detail-view.tsx:85`, `product-icp-editor.tsx:218,237,260`), and no shell file imports either dialog. D1 therefore cannot change anything on a Signals page.
2. **D5, breadcrumb (approach: the new `<ol>` carries `m-0 flex list-none items-center p-0`, the `<nav>` keeps its own classes): IDENTICAL.** 8 captures of the real Signals pages (4 pages x 1280 px and 390 px) and 10 stress cases: every node has the same position, size and style, and the screenshots differ in **0 pixels** (max channel difference 0) in all 18. The only computed value that changes is `list-style-type` on the `<li>`s and their children (before: the inherited initial `disc`, after: `none` from the new `<ol>`); those boxes are `display:flex`, so no marker is ever drawn, which the 0-pixel result confirms. Result line of the tool: `RESULT: no hard difference`.
3. **D1, confirm dialog.** Before the fix the focus stays on the button behind the dialog (`insideDialog:false`, measured with a real mouse and a real keyboard open): the defect is reproduced in a real browser. After: the focus is on **Cancel inside the dialog**. Opened with the mouse: the dialog is **pixel-identical** (0 differing pixels) and every box and style is the same, so every existing caller's look is unchanged (the confirm button stays `destructive` unless a caller passes the new optional `tone: 'default'`). Opened with the keyboard: the only difference is 642 pixels, all inside the Cancel button's box plus its 3 px focus ring (`bbox 336,142 to 411,179` against the button at `338.6,145 71.6x32`): the visible focus ring a keyboard user needs, which is the fix.

## What this does not prove
- It compares the breadcrumb at the two widths and the 10 harness widths, not every page of the app; the breadcrumb markup is one component, so the pages not captured go through the same code. Dark mode was not captured.
- The `ConfirmDialog` look was compared on one representative destructive question (the dialog is the same component for every caller; only the text differs).
