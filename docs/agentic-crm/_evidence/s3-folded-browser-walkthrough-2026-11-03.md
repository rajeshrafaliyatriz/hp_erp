## What went wrong on the way (so nobody repeats it)
- **The first two runs (my script)**: the Discovered table shows 20 of 55 alphabetically and the seeded rows are at the end, so the script looked for `S3 CHECK` rows on page 1 and compared 20 rows with the API's 50; phase 4 depended on a variable set in phase 2. Fixed (search first; first page of 20; Alpha's CRM id re-read from the API).
- **The second run, phase 4 timed out at 120 s waiting for "Linked records"** (`run-1-phases-1-3.log`). A diagnostic page load (`x-diag-account360.cjs`) showed no loop: the page issues about 45 requests (React StrictMode asks everything twice in dev) to a single-threaded PHP server whose statements go to a remote database (about 45 ms each); the tab's `POST /api/org-accounts/for-crm/{id}` took 70 to 84 s in the queue and the heading appeared after about 90 s. Timed alone the 360 costs 41 statements and 2.4 s of database time (16 of them are `information_schema`/`SHOW COLUMNS` existence checks, about 1.2 s); `for-crm` on an existing identity costs 3 statements. Waits were lengthened, the server was restarted with PHP opcache enabled. A production server with a local database and workers is not affected like this; the developer on this stack will feel it.
- **The phases 4 to 8 run, phases 6 to 8, remote database unreachable**: `SQLSTATE[HY000] [2002] ... unreachable network` on the page (`outage-sqlstate-2002-phase6.png`), `ERR_NETWORK_CHANGED`, many 500s. Not counted. The script now reloads a page that opens on such a message (and prints the count: 0 in the last runs).
- **Script faults found by real failures**: the first `section[aria-labelledby]` of the tab is now the agent's panel, not the Linked records card; Playwright's CSS locators pierce shadow roots and matched Next's dev badge (`<div data-next-badge data-status>`, `node_modules/next/dist/compiled/next-devtools`), a third empty `[data-status]`; axe names one element differently on different pages (compare by rule plus markup).
- A stray `S3 CHECK Lima Public Academy` company (id 158) from an earlier attempt was found by a read-only count after a cleanup that said "rows still carrying the mark: 1"; it was added to the state file, cleaned, and the seed redone before the final run.
