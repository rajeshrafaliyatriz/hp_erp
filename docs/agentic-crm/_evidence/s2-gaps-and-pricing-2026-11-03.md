## Rupee pricing, proved on the real MariaDB (dev)

Migrations applied one file at a time: `2026_12_08_100000` (`ai_models.currency` CHAR(3) NOT NULL DEFAULT 'INR'; all 11 existing rows read INR), `…100100` (`ai_usage_events.estimated_cost` DECIMAL(14,6), `cost_currency` CHAR(3), both NULL; 638 existing rows untouched), `…100200` (`g2g_research_runs.ai_cost` DECIMAL(14,4), `ai_cost_currency` CHAR(3)). `ai:set-model-rate --provider=deepseek --model=deepseek-flash --tenant=6 --input=28.8 --output=115.2 --currency=INR`: dry run printed before and after, `--apply` wrote 0.0288 / 0.1152 per 1,000 tokens, a second apply with other numbers refused ("already hold a price. Add --overwrite to replace it"). End-to-end chain (`s2_pricing_chain_dev.php`, 9 of 9, all created rows deleted): a call of 47,350 input and 6,150 output tokens priced when made at **2.07216 INR** (`estimated_cost_usd` left NULL); the run's `ai_cost` **2.0722 INR** with tokens summed; a second call to an unpriced model (Gemini) made the run's cost **unknown (NULL)**; removing it priced the run again; a run that used no AI costs **0.0000 INR**; `ai_cost_usd` is no longer written.

**Where the default price comes from (read from the vendor, not guessed):** DeepSeek's official pricing page (api-docs.deepseek.com/quick_start/pricing, the September 2026 cut): `deepseek-flash` $0.30 per million input tokens (cache miss) and $1.20 per million output at peak; half that off-peak; cache hits cheaper still. The default uses **peak** and ignores cache hits so the estimate is never below the bill. Exchange rate about ₹96 per US dollar: the only figure I could find was a July 2026 one (₹96.5 on 22 July; ₹95.3 on 4 July), so this is a **stated assumption, not today's rate**. ₹28.80 = 0.30 × 96; ₹115.20 = 1.20 × 96. Applied on dev only. Estimated cost of all 114 live signal calls to date at that rate: 956,607 input + 154,346 output tokens = about ₹45.

## Reviewed and fixed during the review

- **Mislabelling hazard created by my own design, found by the pricing track:** the platform's AI module usage screen computed a cost from the rate card with no currency and printed it with a hard-coded `$`. Fixed: `AiModuleController` now returns `cost_currency` (USD for a recorded cost, the rate's own currency for a computed one, and USD for a rate from a host without the currency column), the screen prints each figure with the matching symbol, nothing is converted (no exchange rate exists in the system). New unit test; two of my three mutations were caught; the third (the host-without-the-column default inside `modelRate`) cannot be reached by a unit test because it needs a database, and is covered only for the model-configuration API.
- **Meter:** `AiUsageMeter` sits on every AI call, so I read its whole diff: prices when the call is made, first row with both rates (organisation before platform; a blank organisation row no longer hides a filled platform default), the dollar column written only for dollar prices, an un-migrated host gets exactly the old insert, a pricing failure costs the row its price and never the row, the column check is cached per process (60-second recheck for a missing column). 21 mutations by the track, all caught.
- **Not changed, on purpose:** `UsageController` (the platform's AI usage screen) still reads `estimated_cost_usd` only, so a rupee-priced call shows tokens and no money there, and a mixed total is flagged incomplete. `CapabilityController`'s "Cost (USD)" label stays correct for that column. The owner decides whether to extend them.

## Found

- My first gaps walkthrough had 6 failures, all my script: the word "High" on the empty Fit tab was the signal's real Confidence field, not an invented band; the formula test used the source link, but a link always starts with `http` (the real risk is titles and organisation names, which now carry the test); the Generate checks did not wait for the product list. Fixed and re-run.
- A timing-sensitive test, `GeminiCredentialFailoverTest::test_per_day_quota_cools_down_much_longer_than_per_minute`, failed once in a full PHP run while I was running migrations and scripts at the same time, and not in a quiet full run (1850 tests, only the 3 known non-S2 failures), nor alone three times, nor after any of the new test files.
