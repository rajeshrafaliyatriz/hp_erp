### 3. [HIGH] 'sent_back' permanently destroys the chain and there is no path that reopens it; resubmission silently creates a duplicate leave row

`LeaveApprovalWorkflow.php:211` — *chain-logic*

**Claim:** recordDecision() classifies any decision other than 'approved'/'approved_lwp' as a rejection (LeaveApprovalWorkflow.php:252), so 'sent_back' — an action the new drawer offers as a first-class approver button — sets the current step to 'rejected' and skips every remaining step, permanently ending the chain. Nothing reopens it: store()'s upsert and the legacy ApplyLeaveController both key on `status='pending'`, ApplyLeaveController::update() is an empty stub, and there is no PUT/PATCH route. Three consequences, all real: (a) approvals already collected are silently discarded — the resubmission takes the insert branch (the new overlap guard at line 294 omits 'sent_back', so it blocks nothing, even for an identical from_date) and openFor() builds a fresh chain, making the reporting manager approve the same leave twice, and leaving two live rows for the same dates; (b) the 'sent_back' row can never be closed — destroy() requires 'pending' and cancel() requires 'approved', so it sits in the tenant's list forever; (c) contrary to the original claim it is NOT undecidable — with no 'pending' step left, currentStep() returns null, decision() skips the whole chain block at line 500 and bulkDecision() drops the id into $finalise[], so a single approve_leave holder can move the 'sent_back' row to 'approved' alone, with no chain enforcement at all. The send-back path therefore both destroys collected approvals and creates a route around the multi-level approval the feature exists to enforce.

**Failure scenario:** Chain [reporting_manager, department_head]. The Reporting Manager approves step 1; the Department Head sends the request back at step 2 asking for corrected dates. Step 2 -> 'rejected', request status -> 'sent_back', and the Reporting Manager's step-1 approval is now attached to a dead row. The employee corrects the dates and resubmits: store() finds no pending row, inserts leave #2 with a fresh chain, and the Reporting Manager has to approve the same leave a second time. The tenant is left with two rows for the same dates — one 'sent_back', one 'pending' — and the 'sent_back' one is undecidable and un-withdrawable (destroy() requires status='pending').

**Verifier:** Traced the code; the core mechanism is real, but one asserted consequence is wrong and is in fact inverted.

CONFIRMED parts:
1. LeaveApprovalWorkflow.php:252 `$approved = in_array($decision, ['approved','approved_lwp'], true);` — every other DECISION_STATUS, including 'sent_back', falls to the rejection branch. Line 257 writes the current step `status => 'rejected'`; lines 265-269 flip every remaining `pending|waiting` step to 'skipped'. So a send-back at step 2 of [reporting_manager, department_head] leaves step 1 'approved' on a row nobody can act on through the chain again.
2. No reopen path exists. Controller:373-378 (`->where('status','pending')`) never matches a 'sent_back' row, so the upsert branch is unreachable and line 396+ inserts. routes/api.php `leave` group has index/store/bulk-decision/show/decision/cancel/destroy and no PUT/PATCH on a request. The only other write paths are legacy: `ApplyLeaveController::update()` is an empty stub (line 299-302), `ApplyLeaveController::store()` uses the same `->where('status','pending')` upsert key, and `updateLeave()` only accepts `status == 'cancelled'`. Nothing anywhere sets a leave row back to 'pending' or resets its steps.
3. The overlap guard at Controller:290-297 is `whereIn('status', ['pending','approved','approved_lwp'])` — 'sent_back' is absent, so the resubmission is not blocked. It is not blocked even when the employee resubmits the IDENTICAL from_date, because the upsert lookup also requires 'pending'. Result: two live rows for the same dates, and `openFor()` at line 405 builds a fresh chain that asks the reporting manager to approve again.
4. destroy() (line 847) requires `status === 'pending'` and cancel() (line 779) requires approved/approved_lwp, so the 'sent_back' row can never be withdrawn or cancelled — it sits in the tenant's list permanently.
5. ApprovalChain.tsx STEP_STYLES maps 'rejected' to the note 'Rejected'; a sent-back step renders to the employee as a rejection. LeaveRequestDetailsDrawer.tsx:408 does offer 'Send Back' as a first-class approver action, so this path is reachable from the shipped UI. (No live 'sent_back' rows yet: snapshot shows approved 6 / pending 14 / rejected 1.)

REFUTED part — "the 'sent_back' one is undecidable": the opposite is true, and it is worse. After the send-back every step is rejected/skipped, so `currentStep()` (workflow:182-191, `where('status','pending')`) returns null. decision() then skips the whole `if ($step)` block at line 500 and falls straight to applyDecision() at line 553, which has no status precondition at all (line 900-903: `where('id')->where('sub_institute_id')->update`). So any single holder of approve_leave with scope can push a 'sent_back' row straight to 'approved' on their own, with the chain no longer enforced. bulkDecision() is the same: line 661-664 puts any no-step row into `$finalise[]`. The chain-destruction therefore converts the request into one that bypasses the very multi-level gate F-108/F-124 was built to add. The API is open even though the drawer hides the buttons behind `request.status === 'pending'`.

Also minor: the cited line 211 is `roleMayDecide()`'s `$allowed = ...`; the actual decision-classification line is 252.
